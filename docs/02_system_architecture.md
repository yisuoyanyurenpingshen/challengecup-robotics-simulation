# SmartClean-Sim 系统架构

## 1. 文档目的

本文定义 SmartClean-Sim 的共同架构、模块边界和集成顺序，供仿真、感知、规划、交互和边缘部署成员并行开发。

项目的正式定位是：**面向 RDK 国产机器人平台的智慧环卫无人清扫车仿真与边缘部署验证系统**。

当前已经交付可重复验证的 PC 端二维闭环，通过 ROS2 Humble 回放桥发布状态、轨迹和位姿，并打通 Gazebo 差速车运动闭环；LiDAR/Nav2、YOLO、LLM、Web 和 RDK 仍按适配器边界逐步接入。本文中的“核心”不依赖这些外部系统；外部能力统一通过适配器接入。

## 2. 架构决策

### 2.1 确定性二维核心优先

最小可运行系统采用二维离散仿真核心，负责地图、机器人运动、垃圾目标、禁行区、动态障碍、清扫动作和指标统计。二维核心是算法验证和自动化测试的基准环境，不以逼真的物理渲染为目标。

同一版本代码在输入场景、任务、配置和随机种子相同的情况下，必须产生相同的状态序列、路径和汇总指标。实现时遵守以下约束：

- 使用固定仿真步长 `dt` 和仿真时钟，不用墙上时间驱动核心状态。
- 所有随机行为显式接收 `seed`，禁止模块私自创建不可控随机源。
- 同一时刻的对象按稳定标识符排序处理，避免容器遍历顺序改变结果。
- 外部输入只在仿真步边界进入核心，并记录为领域事件。
- 核心测试默认使用模拟感知和规则任务解析器，不依赖 GPU、网络或在线大模型。

### 2.2 核心与外部平台解耦

核心对象只使用项目定义的数据模型，不直接依赖 ROS2 消息、YOLO 张量、大模型 SDK、HTTP 请求对象或 RDK BPU API。

依赖方向固定为：

```text
CLI / Web / ROS2 / Gazebo / YOLO / LLM / RDK
                    │
                    ▼
                 adapters
                    │
                    ▼
domain ← tasking ← orchestration → perception / planning / control
                    │                         │
                    └──────── simulation ─────┘
                              │
                              ▼
                           metrics
```

允许适配器依赖核心，禁止核心反向导入适配器。外部平台切换时，不应修改规划、状态机或指标定义。

### 2.3 先闭环，后增强

首个闭环只要求：加载场景、接收任务、规划路径、模拟移动、执行清扫、处理障碍并输出指标。真实视觉、自然语言理解、三维物理仿真和板端推理均是增强能力，不能成为基础演示和持续测试的启动条件。

## 3. 系统分层与模块职责

### 3.1 `domain`：领域模型

职责：

- 定义位置、任务、检测结果、路径、机器人状态、控制命令和领域事件。
- 定义坐标、单位、枚举、校验错误和不可变值对象。
- 保持零平台依赖，作为所有模块共享的唯一数据语言。

禁止：读取文件、调用 ROS2、加载模型、发 HTTP 请求或推进仿真。

### 3.2 `simulation`：确定性二维世界

职责：

- 从已校验的场景配置构建世界。
- 维护静态障碍、动态障碍、垃圾、区域、机器人和充电点。
- 按固定步长应用控制命令，更新机器人和动态对象状态。
- 进行碰撞、越界、禁行区和清扫范围判定。
- 生成传感器观测和领域事件。

二维核心只模拟完成算法验证所需的行为，不承担真实车辆动力学、轮胎模型或高保真传感器噪声建模。

### 3.3 `perception`：感知抽象

职责：

- 把观测转换成统一 `Detection` 列表。
- 提供确定性的 `MockPerception`，供集成测试和无 GPU 演示使用。
- 对检测类别、置信度、坐标系和时间戳做标准化。

感知模块只回答“看到了什么、在哪里”，不决定清扫优先级、不生成路径，也不直接控制机器人。

### 3.4 `planning`：任务与运动规划

职责：

- 将目标区域离散为可通行网格。
- 生成覆盖路径、定点目标访问顺序和返航路径。
- 使用 A* 等算法连接关键航点。
- 在障碍变化或路径失效时重规划。
- 返回带原因和诊断信息的 `PlanResult`。

规划器读取世界快照，不直接修改仿真世界。工业级 Nav2 集成属于 ROS2 适配层，不能替换核心接口语义。

### 3.5 `control`：运动与安全控制

职责：

- 根据当前位姿和下一个航点产生速度命令。
- 限制线速度、角速度和加速度。
- 在暂停、故障、急停或安全距离不足时输出零速度。
- 判定航点到达，但不负责全局路径搜索。

二维核心使用简化运动学控制器；真实底盘控制器通过同一控制命令语义适配。

### 3.6 `tasking`：任务解析与执行

职责：

- 校验结构化 `TaskSpec`。
- 提供确定性的规则解析器，将受支持的文本指令转换为 `TaskSpec`。
- 维护任务队列、状态机、暂停/恢复/取消/返航语义。
- 根据计划和感知事件协调规划、移动、清扫及返航。

任何 LLM 输出必须先转成 `TaskSpec` 并完成字段、枚举、区域和安全规则校验，绝不能直接成为速度命令。

### 3.7 `orchestration`：闭环编排

职责：

- 组装场景、感知器、规划器、控制器、任务执行器和指标采集器。
- 固定每个仿真步的调用顺序。
- 接收已校验的外部命令，并在步边界投递。
- 管理启动、运行、结束和资源释放。

推荐单步顺序：

1. 读取本步外部命令。
2. 生成世界观测。
3. 执行感知并更新世界快照。
4. 推进任务状态机，必要时规划或重规划。
5. 由控制器生成控制命令。
6. 推进二维世界一个固定步长。
7. 发布领域事件并采集指标。
8. 检查终止条件。

该顺序一经实现，应通过测试锁定；调整顺序必须记录架构变更。

### 3.8 `metrics`：指标与可追溯结果

职责：

- 订阅领域事件，不反向影响任务执行。
- 统计任务完成率、清扫覆盖率、垃圾清除率、路径长度、仿真耗时、重规划次数、避障次数和碰撞数。
- 输出结构化运行摘要和可选路径轨迹。
- 在结果中记录版本、场景、任务、seed 和关键配置，保证可复现。

比赛指标必须标注为“仿真验证指标”或“实测指标”，不得用仿真结果直接声称满足工业实车指标。

### 3.9 `adapters`：外部系统适配

适配器负责协议转换和资源管理，不承载核心业务规则。

| 适配器 | 输入 | 输出 | 明确边界 |
|---|---|---|---|
| ROS2 | Topic、Service、Action | 核心数据对象或 ROS2 消息 | 已实现只读回放桥与速度安全中继；核心不出现 `rclpy` 和 ROS 消息类型 |
| Gazebo | 速度命令、模型状态、相机、雷达 | `/odom`、TF、`Observation`、`RobotState` | 差速运动已接入；传感器与 Nav2 待接入，不改变任务语义 |
| YOLO | 图像帧 | 标准 `Detection` | 不做路径规划和任务决策 |
| LLM | 自然语言和受限上下文 | 候选 `TaskSpec` | 必须校验；失败时拒绝或回退规则解析器 |
| Web | HTTP/WebSocket | 命令、状态和指标 DTO | 不直接操作仿真内部对象 |
| RDK | 图像、BPU 模型、板端运行时 | 标准 `Detection` 或 ROS2 检测消息 | 板端特有代码不进入核心，PC 与板端保持同一检测契约 |

## 4. 端到端数据流

### 4.1 基础确定性闭环

```text
场景 JSON ──→ 场景校验 ──→ 二维世界
任务 JSON ──→ 任务校验 ──→ 任务执行器
                                  │
二维世界 ──→ 模拟观测 ──→ 模拟感知 ──→ 世界快照
   ▲                                      │
   │                                      ▼
控制命令 ←── 控制器 ←── 路径/航点 ←── 规划器
   │
   └──→ 世界推进 ──→ 领域事件 ──→ 指标采集 ──→ 运行摘要
```

### 4.2 LLM 任务流

```text
自然语言 → LLM/规则适配器 → 候选 TaskSpec → Schema 校验
                                             │
                         非法：拒绝并返回原因 ┤
                         合法：进入任务队列 ──┘
```

### 4.3 RDK 感知流

```text
PC：二维核心 / Gazebo / 规划 / 指标
                      ▲
                      │ ROS2 Humble，ROS_DOMAIN_ID=42
                      ▼
RDK：相机 → 预处理 → BPU 推理 → 后处理 → 标准 Detection
```

RDK 适配验证的是模型转换、量化、板端推理和通信链路；基线为 RDK OS 3.x、Ubuntu 22.04 和 TROS-Humble，X5 为主目标、X3 为兼容目标。在没有开发板时，应使用相同接口的 PC 适配器完成协议验证，并明确标注未进行板端实测。完整部署边界见 `09_rdk_tros_deployment.md`。

## 5. 任务状态机

统一任务状态如下：

| 状态 | 含义 |
|---|---|
| `IDLE` | 无活动任务，可接收新任务 |
| `PLANNING` | 正在生成或检查初始计划 |
| `NAVIGATING` | 沿计划路径前往目标或覆盖区域 |
| `CLEANING` | 在清扫范围内执行清扫动作 |
| `AVOIDING` | 对短时动态障碍执行局部避让或等待 |
| `REPLANNING` | 当前路径失效，重新生成计划 |
| `PAUSED` | 用户暂停，保持任务上下文并输出零速度 |
| `RETURNING` | 返回充电点或待命点 |
| `COMPLETED` | 任务成功结束 |
| `FAILED` | 任务因不可恢复错误结束 |
| `EMERGENCY_STOPPED` | 急停锁定，必须显式复位 |

主要转换规则：

```text
IDLE → PLANNING → NAVIGATING ↔ CLEANING
          │             │          │
          │             ├→ AVOIDING ─┤
          │             └→ REPLANNING ─→ NAVIGATING
          │
          └→ FAILED

NAVIGATING / CLEANING → RETURNING → COMPLETED
NAVIGATING / CLEANING → COMPLETED
任一活动状态 → PAUSED → 原可恢复状态
任一非终态 → FAILED
任一非急停状态 → EMERGENCY_STOPPED
COMPLETED / FAILED / EMERGENCY_STOPPED --reset→ IDLE
```

约束：

- `PAUSED` 和 `EMERGENCY_STOPPED` 状态下控制输出必须为零。
- `resume` 只能恢复普通暂停，不能自动解除急停。
- `return_after_done=true` 时清扫完成后必须先进入 `RETURNING`。
- 所有失败都要携带机器可读错误码和面向人的说明。
- 状态变化必须发布 `StateChanged` 事件，供日志、Web 和 ROS2 统一消费。

## 6. ROS2 集成边界

ROS2 是通信和生态集成层，不是核心算法的唯一运行方式。当前独立工作空间已经建立：

```text
ros2_ws/src/
├── smartclean_core/           平台无关核心与 demo 配置的 ROS 安装包装
├── smartclean_ros/
│   ├── smartclean_ros/      核心调用、坐标转换与 ROS2 节点
│   ├── launch/              回放演示编排
│   └── test/                转换与桥接契约测试
└── smartclean_gazebo/
    ├── launch/              Fortress headless、差速车与 ROS-Gazebo 桥接
    ├── models/              本地差速清扫车 SDF 模型
    ├── test/                SDF 与接口契约测试
    └── worlds/              无在线资源依赖的环卫场景
```

当前已经验证的只读输出：

- `/smartclean/status`：`std_msgs/msg/String`，承载版本化 JSON 状态。
- `/smartclean/trajectory`：`nav_msgs/msg/Path`，发布完整 `map` 轨迹。
- `/smartclean/robot_pose`：`geometry_msgs/msg/PoseStamped`，发布逐帧回放位置。

当前已经验证的 Gazebo 运动链：

```text
/cmd_vel
   ↓
速度安全看门狗（0.5 秒断流或非法数值时输出零速度）
   ↓
/smartclean/safe_cmd_vel → ros_gz_bridge → Gazebo DiffDrive
                                      ├── /odom
                                      └── /tf（odom -> base_link）
```

栅格桥接显式完成“左上原点、`y` 向下、整数格”到“左下原点、`y` 向上、米制 `map` 格中心”的转换。实现、QoS、参数和验证结果见 `08_ros2_environment_and_bridge.md`。

下一段导航闭环的映射目标：

- 已接入底盘接口：`/cmd_vel`、`/odom`、`odom -> base_link` TF。
- 待接入传感器与定位：`/scan`、相机、`map -> odom`。
- 项目消息：`/smartclean/detections`、`/smartclean/robot_state`、`/smartclean/metrics`。
- 项目动作：`/smartclean/clean_area`，支持反馈、取消和最终结果。

ROS2 节点只转换协议并调用核心服务；不得在回调中复制一套独立状态机。ROS2 不可用时，CLI 闭环仍必须正常运行。当前已经证明底盘命令—动力学—里程计闭环，仍不能表述为 `map` 定位—Nav2 规划—`/cmd_vel` 自主导航闭环。

## 7. 故障与降级策略

- YOLO 或 GPU 不可用：切换到 `MockPerception`，结果标明感知来源。
- LLM 超时、离线或输出非法：回退到规则解析器；仍无法解析则拒绝任务，不猜测危险字段。
- ROS2/Gazebo 不可用：使用 CLI 和二维核心完成演示与测试。
- RDK 不可用：仅展示经过验证的接口与转换流程，不声称板端性能。
- 动态障碍短时出现：进入 `AVOIDING`；超过等待阈值则 `REPLANNING`。
- 无可行路径或场景配置非法：进入 `FAILED`，保存诊断信息。

## 8. 实施阶段与完成标准

### 阶段 A：核心闭环

- 场景和任务可校验加载。
- 固定 seed 下结果可复现。
- 支持定点清扫、基础覆盖路径、避障/重规划和返航。
- 输出结构化指标。
- 单元测试和最小集成测试不依赖 ROS2、GPU 或网络。

### 阶段 B：演示接口

- 接入 Web 或 CLI 控制。
- 接入 YOLO，但保留模拟感知开关。
- 路径、状态、检测和指标可视化。

### 阶段 C：机器人生态

- ROS2 Humble 环境与状态/轨迹/位姿回放桥已完成。
- Gazebo Fortress 最小 World 与 ROS-Gazebo `/clock` 冒烟已完成。
- Gazebo 差速清扫车、`/cmd_vel` 安全看门狗、`/odom` 和基础 TF 已完成。
- 标准传感器、完整 TF、Nav2、动作取消和状态反馈待实现。

### 阶段 D：国产边缘适配

- 完成 ONNX 导出、量化/转换说明和 RDK 推理适配器。
- 有硬件时记录板端精度、时延、吞吐和资源占用；无硬件时明确验证边界。

任何阶段完成后，都应同步更新 `docs/` 技术文档和 `logs/` 工程日志，并在提交信息中说明模块、行为变化和验证方式。
